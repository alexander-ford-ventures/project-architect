## Sketch A — Inline validation in `claude-tooling-author`

**Goal:** Catch malformed shell/JSON before the agent declares done. Validates output of `claude-tooling-author` (which now runs in Phase 7, consuming `CLAUDE_TOOLING_PLAN.md`).

**Per-file-type validators:**

| Filetype | Validator | Failure mode |
|---|---|---|
| `*.sh` (any hook) | `shellcheck -s bash -S warning $f` then `bash -n $f` | Capture stderr; retry write up to 2× |
| `*.sh` (executable hooks) | Above + smoke run: `timeout 2 bash $f </dev/null >/dev/null 2>&1` | Same retry loop |
| `settings.json` | `jq empty $f` then `jq -e '.permissions.allow' $f` | Same retry loop |
| `*.json` (other) | `jq empty $f` | Same retry loop |
| Slash commands (`.claude/commands/*.md`) | YAML frontmatter parse via Python yaml.safe_load | Warning only |

**Cost:** +3-5 Bash calls per file. ~5-30s overhead per agent run. No extra dispatches.

**Live-test verdict:** 0 of 13 bugs in this test (all `claude-tooling-author` output was clean), but provides regression-prevention. Ship.

**Note on timer attribution:** During the live test, the elapsed-time display on dispatched agents accumulates wall-clock time including periods when the architect is *waiting on user input* between phases. This means visible "agent took N minutes" can be misleading — the actual agent work may be much less. Implementation should distinguish: (a) agent CPU/dispatch time, (b) user-wait time, (c) total elapsed. Surface (a) for cost analysis; show (c) for user transparency. This is a UX detail of the orchestrator wrapper, not a logic bug, but worth documenting.

## ★ Sketch D — Multi-session lifecycle with design-first + superpowers handoff (REWRITTEN)

**Goal:** Resolve the scope-creep tension by making EVERY executable artifact design-first. Project-architect produces design + plan docs; execution lives in a new Phase 7 (for tooling) or hands off to `superpowers` (for product code).

### The new phase structure

```
SESSION 1 — project-architect
├── Phase 1: Discovery
├── Phase 2: Tech-stack decisions + ADRs
├── Phase 3: Architecture deep-dive
├── Phase 4: Generate design docs + plan docs
│   ├── docs/*.md (existing design docs — README, ARCHITECTURE, etc.)
│   ├── docs/CLAUDE_MD_PLAN.md           ← NEW: describes future CLAUDE.md content
│   ├── docs/CLAUDE_TOOLING_PLAN.md      ← NEW: describes future .claude/* tree
│   ├── docs/SCAFFOLD_PLAN.md            ← NEW: describes future code structure
│   └── docs/NEXT_STEP_PLAN.md           ← NEW: post-restart routing
├── Phase 5: Iteration menu — edit plans before execution
├── Phase 6: LOCK + FINALIZE
│   ├── Snapshot docs/* → docs/versions/{version}/ (full design snapshot)
│   ├── Set state.locked = true; state.version = "v1.0"; state.locked_at = ISO8601
│   ├── KEEP docs/_architect_state.json in place (canonical for /iterate-design)
│   ├── ALSO archive state.json → docs/versions/{version}/_architect_state.json (versioned)
│   ├── Final state.json save
│   ├── Commit everything
│   └── Optional: push to remote (offer; require user opt-in)
│   └── ⚠ DO NOT DELETE state.json — /iterate-design needs it as the canonical entry point
├── Phase 7: TOOLING EXECUTION (NEW)
│   ├── Menu: which plans to execute?
│   │   ├── (a) Execute CLAUDE_MD_PLAN  → generates CLAUDE.md (claude-md-author)
│   │   ├── (b) Execute CLAUDE_TOOLING_PLAN → generates .claude/* (claude-tooling-author + slash commands)
│   │   ├── (c) Hand off SCAFFOLD_PLAN to superpowers (writing-plans → SDD)
│   │   ├── (d) Skip all execution (close out with plans only)
│   │   └── (e) (a) + (b) + offer (c) — the default productive path
│   └── Each chosen execution: agent reads its plan doc + state, writes files, commits
└── Phase 8: HANDOFF (NEW)
    ├── Print: "Design + tooling complete. Restart Claude Code to load CLAUDE.md + .claude/."
    ├── Print: "After restart, the new session will offer scaffold/implement options."
    ├── Print: "To restart: type /exit, then run `claude` in this directory."
    └── Architect run ends

[USER MANUALLY RESTARTS Claude Code in this directory]

SESSION 2 — fresh session, CLAUDE.md is loaded
├── CLAUDE.md greets the new session with project context (auto-loaded by Claude Code)
├── CLAUDE.md presents next-step options:
│   ├── (a) Scaffold actual code: run /scaffold (auto-invokes superpowers chain)
│   ├── (b) Open SCAFFOLD_PLAN.md and review before scaffolding
│   ├── (c) Just orient me; I'll work on docs directly
│   └── (d) Iterate design — re-launch project-architect (state unlock prompt)
└── User picks → proceeds
```

### New plan templates (added in Phase 4)

#### `CLAUDE_MD_PLAN.md`
Describes what the future root `CLAUDE.md` will contain:
- Project context block (name, elevator pitch, tech stack summary)
- Working-in-this-project rules (Conventional Commits, test discipline, etc.)
- Next-step menu (the slash commands users can run)
- Per-subfolder CLAUDE.md plans (if any subfolders exist post-scaffold)

#### `CLAUDE_TOOLING_PLAN.md`
Describes the planned `.claude/` tree:
- `settings.json` permissions allow/deny per ADR-derived security policy
- `hooks/` — list of hooks with bash content blocks
- `commands/` — list of slash commands with their target intents
- `agents/` — any custom project agents
- `recommended-plugins.md` — plugin curation

#### `SCAFFOLD_PLAN.md`
Describes the future code structure (hands off to superpowers for execution):
- Build manifest content (Cargo.toml / package.json / pyproject.toml / etc.)
- src/ tree with file purposes
- License files + NOTICE
- Toolchain pin file
- Includes the EXACT commands superpowers should run (`cargo init --lib --vcs none`, etc.)

#### `NEXT_STEP_PLAN.md`
Routes Session 2:
- Maps each next-step option to specific slash commands
- "If you want to scaffold: /scaffold"
- "If you want to implement a specific feature: /implement <feature-name>"
- "If you want to revise design: re-launch project-architect"
- Includes troubleshooting (e.g., "if /scaffold fails because superpowers isn't installed, here's the manual fallback")

### State file lifecycle (canonical answer)

The state file at `docs/_architect_state.json` is **always preserved** through all phases. Three locations matter:

| Location | Purpose | Lifecycle |
|---|---|---|
| `docs/_architect_state.json` | **Canonical "current" state** | Created in Phase 0; updated through Phase 8; persists indefinitely; consumed by `/iterate-design` |
| `docs/versions/v1.0/_architect_state.json` | Versioned snapshot at lock | Created in Phase 6 alongside docs/* snapshot; never modified after |
| `docs/versions/v1.1-draft/_architect_state.json` | Mid-iteration snapshot (optional) | Created if Phase 5 user requests pre-revision snapshot |

**Three new state fields** (added in Phase 6 LOCK):

```json
{
  "locked": true,                            // false during architect runs; true after Phase 6
  "version": "v1.0",                         // semver-style; "v1.1-draft" after /iterate-design unlock
  "locked_at": "2026-05-13T01:23:45Z"       // ISO8601 timestamp; null when unlocked
}
```

**The "delete state file" option (was Phase 6 substep option 1 in the original spec) is REMOVED.** It was incompatible with `/iterate-design` and made the multi-session story impossible. The architect run instead always preserves state — that's the whole point of having it persistent.

### ★ Per-phase memory persistence (added 2026-05-13 round 5)

**Goal:** Make project-architect runs visible to fresh Claude Code sessions opened in *any* directory, not just sessions that `cd` into the project.

**Why state.json isn't enough:** state.json is project-scoped (lives at `docs/_architect_state.json`). When you open a fresh session in another folder, Claude has no idea your md2pdf project exists or what state it's in. Memory is user-scoped (lives at `~/.claude/projects/.../memory/`) and is auto-loaded into every Claude session — so an entry there means cross-session continuity by default.

**Cadence: write/update memory at every phase boundary.** After-each-batch is too noisy; after-only-at-lock loses crash recovery. Phase boundaries are the right level — 8-9 writes per architect run.

| Phase | Memory action |
|---|---|
| 0a (domain research) | **Create** initial memory entry — project exists, type, elevator pitch |
| 1 (vision/scope) | Update — vision summary, scope decisions |
| 2 (tech stack + ADRs) | Update — stack summary, ADR count, key choices |
| 2.5 (cost modeling) | Update — verdict ($/mo) |
| 3 (architecture + ADRs) | Update — architecture decisions, ADR count |
| 4 (doc generation) | Update — doc count, doc list |
| 5 (iteration) | Update on each revision wave — what changed |
| 6 (lock) | **Major update** — mark `LOCKED at v1.0`, link to snapshot |
| 7 (plan handoff) | Update — plan path, "ready to execute via /scaffold" |
| 8 (handoff) | Final update — restart instructions, slash command list |

**Memory entry shape:**

```markdown
---
name: project-architect — {project_name}
description: {one-line current status}
type: project
---

**Status ({date}): {phase} — {locked|in-progress|draft}**

- **Project**: {name} ({elevator_pitch})
- **Path**: {project_dir}
- **Tech stack**: {one-line summary}
- **Decisions**: {N} ADRs filed (latest: {title})
- **Docs**: {M} generated in docs/
- **State**: docs/_architect_state.json (canonical) + docs/versions/{version}/ (snapshot if locked)
- **Plan**: {plan path or "not yet"}
- **Last action**: {state.last_action}

**To resume in a fresh session**:
- `cd {project_dir}` then `/project-architect` — offers resume/iterate based on state
- Or `/scaffold` (post-lock) to invoke superpowers:writing-plans + SDD against SCAFFOLD_PLAN.md
```

**State.json gets a new field:** `state.memory_pointer: { name, path, last_synced }`. After the first memory write in Phase 0a, every subsequent phase update reads this pointer to find/edit the same entry. If memory is missing or moved, regenerate from state and update pointer.

**MEMORY.md index entry** (added on first write, kept ~150 chars):

```
- [project-architect — {name}](project_architect_{slug}.md) — {phase}; {N} ADRs; {locked/in-progress}
```

**Cost:** ~30 LOC of orchestrator logic. One Edit per phase boundary (~200-400 chars touched). Negligible vs. cross-session continuity win.

**Failure modes & mitigations:**
- **Memory write fails (disk full, perms)**: log warning, continue. State.json is still authoritative for in-project resume; only cross-session discovery is lost.
- **Two architect runs on same project**: each has its own memory entry, distinguished by project name. State.json prevents concurrent edits via lockfile (existing pattern).
- **Memory drift from state.json**: every phase update overwrites with current state. No manual reconciliation needed.

**Live-test verdict for this addition:** During the md2pdf live test, no memory entry was created automatically — only the manual entries I (the parent session) wrote. A fresh session opened in `/private/tmp/pa-test-cli/` would have to re-read state.json from scratch; a session opened elsewhere would have no idea md2pdf existed. With per-phase memory updates, both cases are solved.

### Why this is better than the previous Sketch D (code-emission chain)

- **Architectural cleanliness**: project-architect = "what to build + why"; superpowers = "how to build". The line is no longer fuzzy.
- **No agent duplication**: `superpowers:subagent-driven-development` already provides planner/implementer/spec-review/code-quality-review/fixer. Building Sketch D-original would have duplicated it.
- **Better Phase 5 power**: users can edit *plans* before execution; with the old direct-generation, Phase 5 could only re-trigger agents.
- **Multi-session story**: makes the "design now, build later" workflow first-class, not a hack.
- **Graceful degradation**: if superpowers isn't installed, /scaffold prints manual instructions from SCAFFOLD_PLAN.md.

### What's lost vs the previous Sketch D

- Slightly more friction: user must restart Claude Code between Sessions 1 and 2.
- Project-architect can no longer guarantee "buildable project at end of run" — the build happens in Session 2.
- (Mitigation): Phase 7 still creates CLAUDE.md + .claude/ in the same session, so the *Claude Code experience* is fully bootstrapped at end of Session 1.
